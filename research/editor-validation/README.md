# Editor validation (scripted)

`validate.js` drives the **built** Electron app over the DevTools protocol (`--remote-debugging-port=9350`) using **real mouse and keyboard events** against the production editor (the `#debug` URL hash installs `window.__wts`, which exposes in-renderer objects only). It is **automation, not hand-testing by a person**. It covers Phase 4 (Layers panel, inspector, selection, rename, lock/visibility, reorder, properties, add/duplicate/delete, multi-selection, group/ungroup, 50+ layers, accessibility scan, save/reopen) plus Phase 3B regression checks (drag, resize, rotate, off-canvas, snapping, zoom, exact-size render, Node isolation).

Run: `npm run build`; launch `WALKONE_DEV_UNSAVED_CHOICES=discard WALKONE_DEV_SAVE_PATH=<tmp>/V.boothproject WALKONE_DEV_OPEN_PATH=<same> npx electron out/main/index.js --remote-debugging-port=9350 --user-data-dir=<tmp>/ud`; then `node research/editor-validation/validate.js`. Native dialogs are answered by the dev-only env overrides (ignored by packaged builds). `results.json` is the recorded Phase 4 macOS run (97/97). `validate-4b.js` (Phase 4B) launches the built app itself, kills it with SIGKILL and relaunches it on the same user-data dir to validate close/quit prompts, autosave and crash recovery (40/40 in `results-phase4b.json`). Screenshots go to a git-ignored `shots/` folder.

**Phase 4C:** `validate-4c.js` (97 checks at 4C; 99 since B3/B3.1, in both right-column states, `results-phase4c.json`) launches the built app itself for each scenario (welcome, editor, recovery, autosave issue, four window sizes via the dev-only `WALKONE_DEV_WINDOW_SIZE`) using the shared `harness.js`. `validate.js` was adapted to the redesigned UI (menus for Close/Open/Save As/stacking/Add layer; run with the `WALKONE_DEV_*` variables exported for both the app and the script) and still passes 97/97; `validate-4b.js` still passes 40/40. All are automation, not human testing, and screenshots (`shots/`, git-ignored) are for human review.

**Phase 4D:** `validate-4d.js` (6 checks, `results-phase4d.json`) sweeps the renderer viewport from 1100 to 1920 px in 40 px steps with DevTools device-metrics emulation (not real frame dragging) and records computed-style facts for the polish items.

**Phase 5A:** `validate-5a.js` (53 checks, `results-phase5a.json`) launches the built app, generates fixture images (PNG via zlib; JPEG/WebP/large JPEG via Pillow), and covers import (all formats), drawer, add/move/resize/rotate, roles, save/reopen, alpha pixel sampling, background fit modes, dedup, error model, remove used/unused, replace, drag and drop at three zoom/pan states (synthetic DataTransfer events through the real handlers), SIGKILL recovery with assets, and the security boundary. Dev-only dialog override added: `WALKONE_DEV_IMPORT_PATHS` (files separated by `|`, dialogs by `;`, `CANCEL`). Automation, not human testing.

**Phase 5B:** `validate-5b.js` (39 checks, `results-phase5b.json`) covers the strip New Project dialog, Design / Print Preview, sheet pixel checks, nudging at four zooms, exact selection X/Y, align/distribute, group X, save/reopen. ## Windows (after Phase 6C)
The self-launching suites run on Windows too. `harness.js` holds the platform conventions: `PY` (`python` on Windows), `MOD_BIT` (Ctrl instead of ⌘ for DevTools key events), `keyLabel` (shortcut labels as the app shows them), `SERIF`/`SANS` (fonts present on a stock install: Didot/Helvetica on macOS, Times New Roman/Arial on Windows) and `quitElectron` (a normal quit). 5C's pointer-centred zoom check allows one screen pixel at the starting zoom (at fit zoom on a 125 % display that is several design pixels). `validate-import.js` check 9d compares live dslrBooth `<Text>` boxes separately (6C C1); none of the five local fixtures has live text, so it reports "nothing to compare" until a sample is added.

## B3.1: the responsive right-column contract and `WTS_VALIDATE_SIZE`
The right column is **Properties above Layers at ≥ 860 CSS px tall and Properties | Layers tabs below** (`rightColumnLayout`). A 1440×900 window is ≈1440×872 CSS px on macOS (stacked) but ≈1426×779 at Windows 125 % and ≈1422×853 at 100 % (tabs). Suites must reason from the ACTUAL CSS height, never assume both panels exist: `h.STANDARD_SIZE` is the standard launch size, `h.rightColumn(c)` reports the rendered layout and the expected one, `h.showPanel(c, 'layers'|'properties')` brings a panel on screen (a tab click in the tabbed state; nothing when stacked). To run any suite in the tabbed state on a Mac: `WTS_VALIDATE_SIZE=1440x807 node research/editor-validation/validate-4c.js` (1440×779 CSS). 4C, 5C and 7b-b2 are verified in both states. Do not make the app stack the panels to satisfy a test.
