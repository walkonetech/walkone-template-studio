**Decision:** `TemplateProject` is our own schema ([DATA_MODEL.md](DATA_MODEL.md)). **Consequences:** DSLR Booth structures never leak into core.

**Decision:** `DSLRBoothImporter` / `DSLRBoothExporter` convert to/from the internal model. **Consequences:** tolerates DSLR Booth format changes; mapping isolated and tested.

**Decision:** editor works offline; data stored locally. **Consequences:** integrations degrade gracefully.

**Decision:** `schemaVersion` + forward migrations with fixtures. **Consequences:** backward compatibility obligation. The exact meaning of the number and when to bump it: ADR-060.

**Decision:** Magnific/Freepik, Envato, etc. live under `integrations/<provider>`; core independent. API availability is unvalidated.

**Decision:** owner-supplied exports in `tests/fixtures/dslrbooth/` are golden references; never fabricate. See [TESTING_STRATEGY.md](TESTING_STRATEGY.md).

## ADR-009 — Native project format: single-file `.boothproject` package — Accepted (Phase 2B)
**Decision:** the portable project is one ZIP-compatible file, `.boothproject`, containing `project.json` and `assets/` (copies of all used assets). Loading is strict: only those two kinds of entries are accepted; unsafe paths, links, encryption, duplicates, case collisions and unreferenced assets are rejected or reported. No separate container version: the layout evolves under `TemplateProject.schemaVersion`. Active work happens in an app-managed working session, not by rewriting the archive. See [DATA_MODEL.md](DATA_MODEL.md) §7.

## ADR-010 — Geometry units and coordinate space — Accepted (Phase 2)
Hybrid: project stores physical size (inches) + DPI; pixel size is derived; layer geometry is stored as numbers in design-canvas pixels at the design DPI. DPI changes only via the explicit `rescaleProjectDpi` operation. Evidence: [fixture analysis §18](../research/DSLRBOOTH_FIXTURE_ANALYSIS.md). Implemented in `src/domain/print`.

Resolved by the Phase 3A spike. Original criteria: large-canvas/HiDPI performance, rotation/resize handles, snapping/guides, React integration, export fidelity/determinism, independence from our serialization, maintenance/licensing, testability.

Likely library index/recents; whether anything else uses it is undecided. Native module packaging considerations.

Accepted so far: Electron, React, TypeScript, Vite (electron-vite), zod, Vitest, Konva/react-konva, **Zustand (ADR-030)**, yauzl/yazl (instead of JSZip, ADR-025). Still proposed/not installed: Sharp, fast-xml-parser, SQLite.
Direction only; confirm per phase when introduced.

## ADR-014 — Preview/export rendering approach — Accepted (Phase 6A, owner-approved 2026-11-16)
**Decision:** the existing **Konva exact-size pipeline** (`renderProjectToCanvas` / `renderOutputToCanvas`, the same node specs the editor and Print Preview use) is the production renderer and is authoritative for every exported pixel. No Sharp and no second rendering engine unless a real blocker appears. The main process only chooses the destination, verifies the bytes (PNG signature, exact pixel size), records density (`pHYs`), builds ZIPs, writes atomically and reveals files. See [ADR-041](#adr-041--production-render-and-general-export-foundation--accepted-phase-6a).
**Consequences:** one rendering definition, so preview and export cannot drift; output is deterministic on one machine (same project → same bytes), but anti-aliasing and font rasterization may differ slightly between macOS and Windows Chromium builds (**Needs Validation** on Windows); rendering runs in the renderer process, synchronously per file (fine for 4×6 at 600 DPI; very large canvases would need tiling).

## ADR-015 — Font strategy (system vs bundled, licensing) — Accepted in part (Phase 5D); embedding OPEN
Resolved by [ADR-039](#adr-039--font-discovery-requested-family-preservation-and-fallback--accepted-phase-5d): system fonts only, the requested family is preserved, availability is detected and reported, rendering uses a fixed fallback stack. **Phase 6A:** every vendor-neutral export is raster, so text is rasterized by Konva with the exporting computer's fonts; a missing font is a preflight warning (the fallback is used). **Still open:** embedding or bundling font files (licensing review required) and the native-vs-rasterized text rule for the DSLR Booth adapter (Phase 6B; see research/DSLRBOOTH_748_RUNTIME_FINDINGS.md).

## ADR-016 — Build tooling: electron-vite, Vite 7, ESLint + Prettier — Accepted (Phase 1)

**Context:** Phase 1 needed one build pipeline for main, preload and renderer. **Decision:** use `electron-vite` (which wraps Vite). Vite is pinned to `^7` and `@vitejs/plugin-react` to `^5` because `electron-vite@5` supports Vite 5–7 only. Keep `package.json` without `"type": "module"` so the sandboxed preload stays CommonJS. Prettier skips Markdown to avoid churn in docs. **Consequences:** upgrade Vite only when electron-vite supports it. Zustand, Sharp, JSZip, fast-xml-parser and a test runner are not yet installed (ADR-013 stays Proposed).

## ADR-017 — Adapter-scoped source compatibility metadata — Accepted (Phase 2; population is future)
Optional `sourceCompatibility` map keyed by adapter id, holding `project`-level values, `layers` entries keyed by layer id only where needed, and `unmapped` verbatim data, all JSON-only. The core model stays vendor-neutral and the editor ignores it. Layer copies don't inherit entries; the exporter decides validity of stale values. Populated by the DSLR Booth importer in a later phase.

## ADR-018 — Runtime validation with zod — Accepted (Phase 2)
**Context:** project files must be validated on load with located errors, and types should not drift from validation. **Options:** hand-written validators (no dependency, but duplicated types and many bespoke checks), valibot, zod. **Decision:** zod 4 (`strictObject` to reject unknown keys, discriminated unions for layers); types are inferred from schemas; cross-field rules live in `checkProjectIntegrity`. **Consequences:** one runtime dependency; domain code imports zod only; schemas are the single source of truth.

## ADR-019 — Test runner: Vitest — Accepted (Phase 2)
Fits the Vite/TypeScript stack and needs no extra transform setup; node environment; `npm test`. Component/E2E tooling is not chosen yet.

## ADR-020 — Image roles instead of separate layer types — Accepted (Phase 2)
`ImageLayer.role` (`background|overlay|frame|badge|logo|graphic`) rather than distinct Background/Overlay/Frame interfaces: they share all fields and DSLR Booth stores them identically. A solid background is `canvas.backgroundColor`.

## ADR-021 — Flat layer storage with `parentId` — Accepted (Phase 2)
Groups don't own children; children point to the group. Easier serialization, duplication, reparenting and undo; matches flat canvas-library lists. zIndex is per sibling set.

## ADR-022 — IDs, timestamps, colors — Accepted (Phase 2)
UUIDv4 via `crypto.randomUUID()`; ISO 8601 UTC strings; lowercase hex `#rrggbb[aa]` with literal-or-palette-reference `ColorValue`.

## ADR-023 — Domain location and dependency direction — Accepted (Phase 2)
`src/domain/` is a dedicated pure-TypeScript module (no Electron/React/DOM), imported by renderer, main, tests and future adapters via the `@domain` alias; `src/shared` stays for IPC contracts. Domain imports nothing from the app.

## ADR-024 — Design canvas vs output composition — Accepted (Phase 2)
Authoring canvas and print sheet are separate; `single` or `grid` arrangement of unrotated copies at equal DPI. DSLR Booth two-up (duplicated elements on a larger canvas) is produced by the exporter.

## ADR-025 — Archive implementation: yauzl + yazl — Accepted (Phase 2B)
**Context:** need path-safe extraction, deterministic creation, low memory with large rasters, Node/Electron main only. **Options:** JSZip (promise API, but loads whole archives in memory, no built-in traversal protection), fflate (tiny and fast, in-memory buffers), yauzl/yazl (stream- and file-based, random-access reading, strict file-name validation, per-entry mtime/mode control). **Decision:** `yauzl` (read) and `yazl` (write), plus their type packages. Assets are streamed between disk and archive; hashes are computed while streaming. **Consequences:** two small CommonJS dependencies kept external in the main bundle; no browser/renderer ZIP capability (not needed). JSZip remains unnecessary for native projects; DSLR Booth ZIP handling can revisit the choice.

## ADR-026 — Recent projects stored in a small JSON file — Accepted (Phase 2B)
A bounded (10) JSON list in the app-data directory; no SQLite. It stores only path, name, project id and time, tolerates corruption, and flags missing files. SQLite stays reserved for library/index features (ADR-012).

## ADR-027 — Working sessions and dirty state — Accepted (Phase 2B)
Each open project has a unique session directory under `<userData>/sessions/` holding the working `project.json`, `assets/` and `session.json` recovery metadata. Autosave writes only the working manifest. "Dirty" = serialized project hash differs from the last successful portable save; only Save/Save As/Open make it clean. Clean sessions are deleted on close; sessions with unsaved changes survive an unclean exit for future recovery.

## ADR-028 — Atomic save strategy — Accepted (Phase 2B)
Write a temp file beside the destination, verify it by reopening, fsync, then rename over the destination; fall back to backup-and-swap when the OS refuses to rename over an existing file, restoring the backup on failure. The existing file is never truncated. Windows behavior is implemented per Node semantics but has not been tested on Windows.

## ADR-029 — Canvas rendering/editing engine: Konva + react-konva — Accepted (Phase 3A)
**Context:** the editor needs a print-resolution canvas (2400×3600 design px at 600 DPI) with selection, transforms, photo placeholders, text, shapes, groups, off-canvas geometry, z-order, snapping, crop/clip and exact high-resolution export, over a vendor-neutral domain model that must stay authoritative. **Alternatives:** Fabric.js 7.4.0 (imperative, richer text editing) and Konva 10.7.1 with react-konva 19.3.0 (declarative). **Evidence:** both were implemented against the same domain-built scene and driven with real mouse events on macOS; both passed every functional check (selection, drag/resize/rotate, off-canvas without clamping, z-order, lock/hide, groups, text, snapping, crop, destroy/recreate, zoom independence, 2400×3600 and 1200×1800 exports, Retina) and performed far beyond need at ~110 objects. Differences: Konva needed fewer special cases (Fabric: default origin center, `strokeWidth` 1 in the bounding box, `uniformScaling`, and `objectCaching` all had to be changed for pixel-exact export; image size is scale), the declarative scene removes hand-written reconciliation, groups and z-order are simpler, and the bundle is smaller (194 kB vs 299 kB min). Fabric is ahead on built-in inline text editing and TypeScript typings. Weighted score 3.96 vs 3.61 (high-priority criteria 3.89 vs 3.44). Details: [../research/CANVAS_LIBRARY_EVALUATION.md](../research/CANVAS_LIBRARY_EVALUATION.md). **Decision:** use Konva with react-konva as the editor canvas engine, behind our own engine contract; library objects are never persisted or stored in domain state. **Consequences:** inline text editing will use an HTML overlay; stable-callback pattern needed for the React 19 `react-hooks/refs` lint; Konva's loose config typing must be wrapped; if rich on-canvas text editing becomes a core requirement the choice can be revisited because only the adapter is engine-specific. Fabric was removed from dependencies; its spike remains in git history (`693be9e`). Phase 3B builds the real canvas from the retained pure modules (`geometry`, `viewport`, `snap`).

## ADR-030 — Editor state: Zustand vanilla store over pure mutations — Accepted (Phase 3B)
**Context:** the editor needs shared state (project, selection, view, interaction, snapping) usable from React, Konva event handlers and tests, with the project as the single source of truth. **Alternatives:** React context/reducer; Redux Toolkit; Zustand. **Decision:** Zustand (5.x) using the vanilla `createStore` so the store has no React dependency and can be driven in Vitest; project changes are **pure functions** (`src/editor/mutations.ts`) applied through one `commit` action; Electron access is an injected `EditorPorts` object. The store holds the project exactly once (no second copy of geometry); Konva handlers read it with `getState()` rather than closing over React state or refs. React reads it through `useStore(selector)`; selectors must return stable values (a selector that builds a new object each call loops, which was hit and fixed with `useViewTransform`). **Consequences:** one small dependency; store logic fully unit-tested without Electron; undo/redo, dirty state and working-copy writes live in one place.

## ADR-031 — Undo/redo: snapshots with structural sharing — Accepted (Phase 3B)
**Context:** undo must exist before dozens of editor actions do. **Alternatives:** command pattern (an inverse per action), patches, snapshots. **Decision:** snapshots of the immutable `TemplateProject`; because every mutation shares unchanged layers, a snapshot is a cheap reference. History (past/future, limit 200) covers project content only: selection, zoom/pan, guides, snapping and interaction mode are outside it. A transform/drag commits ONE mutation at interaction end (so one entry); rapid same-key edits (arrow-key nudges) coalesce within 600 ms; a new edit clears redo; opening/creating a project resets history. Dirty = `project !== savedProject` by reference, so undoing back to the saved snapshot is clean. **Consequences:** every future mutation is undoable for free; memory grows with distinct layer objects (bounded by the limit); if projects become huge, patches can replace snapshots behind the same API.

## ADR-032 — Loading project images: IPC byte bridge, no new protocol — Accepted (Phase 3B)
**Context:** the sandboxed renderer must show project-owned images without filesystem access and without weakening the CSP. **Alternatives:** custom `app-asset://` protocol (needs privileged scheme registration, CSP `img-src`, and CORS headers to keep the canvas untainted); blob/data URLs created in main. **Decision:** `project:readAsset` IPC takes `{sessionId, assetId}` (never a path); main resolves the asset from the validated project record, confines the path to the session `assets/` directory, size-caps (256 MB) and returns bytes; the renderer decodes raster images with `createImageBitmap` (no URL, untainted canvas) and SVG through an `<img>` with a `data:` URL (already allowed). The CSP is unchanged. Decoded images live in an `ImageCache` keyed by session+asset and are released when the session closes. **Consequences:** bytes cross IPC once per asset (fine for desktop-sized files; revisit with a protocol or streaming for very large assets); main-process asset index follows `updateWorkingCopy`, so newly added assets must be registered there first.

## ADR-033 — Layer-management rules: order, selection, multi-select, grouping, commits — Accepted (Phase 4)
**Order:** the Layers Panel shows the REVERSE of canvas paint order per sibling set (top of panel = front); the persisted `zIndex` model is unchanged and ties break by array order in both views (`buildPanelRows` vs `sortedSiblings`), with a test that panel and canvas agree. **Selection:** the store holds `selectedIds` (multi-selection implemented). Canvas click selects the OUTERMOST group (a group behaves as one object); Alt/Option-click selects the clicked layer itself; clicking a row in the panel selects exactly that layer (child or group); pressing something already selected keeps the selection, so a panel-selected child can be moved on its own; Cmd (macOS) / Ctrl (Windows) or Shift click toggles on the canvas, Cmd/Ctrl-click toggles and Shift-click selects a visible range in the panel. Locked and hidden layers can be selected from the panel (so they can be unlocked/shown) but are never selectable by canvas click and never get transform handles. **Multi-selection** uses one shared Konva Transformer; Konva drags all attached nodes together; one interaction commits ONE mutation; bulk operations act on the topmost selected layers only so a group and its own child are never processed twice. **Reorder:** pointer-based drag within the same parent (no DnD library); cross-group drops are refused with a message. Stacking commands move selected siblings as a block. **Grouping:** `Group` wraps same-parent siblings (positions unchanged, group takes the topmost member's stacking slot); `Ungroup` returns children in place and folds the group's opacity/hidden/locked into them so the picture does not change. **Commit semantics:** inspector fields keep a text draft and commit on Enter/blur (Escape discards), one undo entry per committed edit; an edit that changes nothing is a no-op and creates no history; continuous color-picker input coalesces. **Consequences:** a documented selection model with a few modifier rules; cross-group drag and drag-into-group are deferred; group opacity/rotation controls are not exposed.

## ADR-034 — Unsaved-changes protection, autosave and crash recovery — Accepted (Phase 4B)
**Close/quit lifecycle.** One main-process `CloseCoordinator` decides every close path (Close Project, Open, New, New Sample, window close, Cmd+Q/app quit). The renderer owns document state but is not the only guardian: main asks it for the state (`document:request`, 1.5 s timeout, treated as "no state, proceed") and shows the **native** Save / Don't Save / Cancel dialog. Cancel, a dismissed dialog, a failed Save, or a cancelled Save As abort the close (the app stays open); Don't Save and a successful Save proceed. Concurrent requests (window close + Cmd+Q) share one in-flight decision, so there is one prompt. Window `close` and `before-quit` call the same coordinator; after approval main sets an approval flag and re-issues the close/quit, and `service.closeAll()` removes sessions only once the close has really succeeded. On macOS closing the last window does not quit (standard); Cmd+Q and Dock Quit take the `before-quit` path; reopening via the Dock creates a fresh window. A single main window and a single instance (`requestSingleInstanceLock`) are assumed. Renderer-initiated closes (Close Project, replace) use the same coordinator via `document:requestClose`.
**Autosave.** The renderer store debounces (2 s, max wait 10 s, retry backoff) and writes ONLY the working session (`updateWorkingCopy`). It never builds a `.boothproject`, never clears Modified, is not in undo history, does not fire for view/selection changes or when content is unchanged, and failures never throw into the UI: status is Saved / Modified / Recovery copy saved / Autosave issue (after repeated failures).
**Session metadata.** `session.json` gains `ownerToken` (random per run), `projectName`, `baselineHash`, `changedFromBaseline`, `portableFileStamp` (mtime+size of the portable file at last save/open), `endedCleanly`, `recoveredAt`; the project schema and `.boothproject` format are unchanged. Ownership is by token, not PID alone (PIDs are reused); the PID is informational.
**Recovery lifecycle.** At startup (before the window) `scanRecovery` examines sessions not owned by this run: clean/ended-cleanly or never-edited sessions (`changedFromBaseline` false and never saved) are deleted; corrupt metadata/manifest and sessions older than 30 days are **quarantined** (moved to `<userData>/session-quarantine`, purged after 60 days), never deleted outright and never fatal; everything else is a candidate. Recent unsaved work is never auto-deleted. A temporary accessible dialog lists candidates (Recover / Discard with a confirm step / Decide later, Escape = decide later).
**Recover semantics.** Recovery loads into memory as a new session, stays Modified, and never writes the portable file. Assets are validated (`recovery-asset-missing`, `recovery-corrupt`). The portable file association is kept only when the file is unchanged since the last save (stamp compare); if it changed or vanished the project is recovered **without** association with a warning (`recovery-conflict` class), so Save becomes Save As and neither side is silently overwritten. Untitled projects recover as untitled. Undo history after recovery starts fresh (history is not persisted).
**Errors.** autosave-failed, recovery-corrupt, recovery-asset-missing, recovery-conflict, recovery-discard-failed. **Dev overrides.** `WALKONE_DEV_UNSAVED_CHOICES` (`save|discard|cancel`, `;` sequences) answers the native prompt for scripted validation; ignored when packaged. **Consequences:** `window.confirm` is gone; Phase 4C can restyle the temporary dialogs without changing behavior. The recovery dialog and prompts are functional only, not designed.

## ADR-036 — Project assets and image import — Accepted (Phase 5A)
**Context:** a real template needs raster artwork; the model (`AssetReference`, `ImageLayer`) and the `.boothproject` assets/ folder already existed. **Decision (no schema or package-format change; schemaVersion stays 1):**
1. **Boundary.** The renderer never supplies a filesystem path. Two narrow IPCs: `project:importAssets` (main shows the native picker, then imports) and `project:importAssetData` (dropped files: the renderer sends bytes + display name). Bytes are used for drops because the sandboxed renderer cannot, and should not, read paths; main only reads paths the user chose in its own dialog.
2. **Ownership.** Import = validate → hash → copy to `<session>/assets/<assetId>.<ext>` (temp file + rename) → `AssetReference` returned to the renderer, which adds it to the project in the same history entry as any layer it creates. The stored name is id-based and the extension comes from the detected format, so different files with the same name cannot collide (the `duplicate-name-conflict` error is therefore unnecessary). Source files can disappear afterwards.
3. **Detection and metadata** come from file bytes, not extensions: PNG, JPEG, WebP, SVG (no PDF/PSD/AI/EPS). Dimensions/alpha are parsed from headers (no Sharp: Electron/Chromium decodes for display and thumbnails; header parsing avoids a native module). Pixel data is fully decoded only when first drawn, so a damaged-but-header-valid file shows "Preview unavailable" rather than failing the import. Limits: 256 MB per file, 150 MP, 8 MB per SVG. SVG stores its intrinsic size in `pixelWidth/Height` (vector: no DPI).
4. **De-duplication** by SHA-256 + byte size within the session: identical content reuses the existing asset (the user is told); names never decide identity; hashing happens once, at import. The session remembers every asset it has seen, so an import that was undone is reused if re-imported or redone.
5. **Undo and files.** Importing is project content and undoable (asset record + layer = one step). Files stay in the session after undo or removal (redo needs them); package writes carry only referenced assets; orphans are deleted when a crashed session is recovered and with the session on close.
6. **SVG policy:** untrusted. It is *rejected* (`unsafe-svg`), never silently rewritten, if it has script/foreignObject/iframe/embed/object/audio/video/link/meta, `on*` handlers, `javascript:`/`vbscript:`/HTML data URLs, entities or an internal DOCTYPE subset, a stylesheet PI or `@import`, or any `href`/`url()` that is not `#id` or an embedded raster data URL. It is drawn only as an `<img>` data URL (no script, no external loads, never inserted in the DOM). CSP unchanged. The text scan is conservative on purpose.
7. **Effective resolution** = designDpi / (layer pixels per source pixel; by fit mode, worst axis for stretch). Starting thresholds (Proposed, owner may tune): ≥300 healthy, 150–299 caution, <150 low (300 dpi is the common photo-print target; below ~150 photographic art looks soft).
8. **Initial size:** native pixels if within 80% of the artboard, otherwise scaled down to 80%; never upscaled; vectors fit to 50%. Drop → centred on the drop point converted through the view to design coordinates (never stored in screen space).
9. **Background** is an ordinary ImageLayer (`role: background`): "Set as Background" keeps one such layer (replacing its asset), sizes it (cover / contain / original), locks it and sends it to the back. **Replace** is per layer only (global replace is ambiguous and deferred). **Remove** is allowed only for unused assets.
10. **Two-up/strips:** assets belong to the logical design; nothing here duplicates assets for a two-up sheet (a later compositor duplicates the whole design).
**Consequences:** bytes cross IPC once per asset per use (import, then canvas decode, thumbnail only if not already decoded); a large-asset bottleneck has not been observed (a 17 MB JPEG imported in ~0.2 s). Header-only validation cannot catch pixel-level corruption. Alternatives rejected: Sharp (native module, packaging cost), renderer-supplied paths (privilege), sanitizing SVG by rewriting (silent alteration).

## ADR-037 — Derived print composition, Design / Print Preview, selection geometry — Accepted (Phase 5B)
**Context:** a 2×6 strip is authored once and printed twice on a 4×6 sheet; authoring two strips by hand lets them drift (the real Chaney template's second frame sits at X 1182 vs −4 on the first, the badge 3 px lower). **Decision (no schema change; schemaVersion stays 1):**
1. The existing `canvas` (DesignCanvas) + `output` (OutputComposition) model is sufficient: 2×6 design, 4×6 output, `grid` 2×1, gap 0. `createProject` now defaults the `strip-2x6-*` presets to that two-up output (other presets stay single). No printer, cut or device field exists in the project; the 2-inch cut is guidance text only.
2. **Copies are derived, never stored.** `planOutput(project)` (pure, `src/canvas/rendering/composition.ts`) translates the authored layer list by each cell origin (`outX = srcX + cellX`); everything else on a layer is untouched and the source project is never mutated. Sizes come from physical size × DPI, not hardcoded pixels. Assets are shared (one `AssetReference`, one decoded image in the cache); PhotoNumbers stay 1,2,3 in the project and repeat only on the sheet.
3. **One drawing path.** `renderOutputToCanvas` (exact-size sheet) and the Print Preview canvas draw each copy through the same node specs as Design mode. Not exposed as a user export (Phase 6).
4. **Clipping:** each copy is clipped to its own design cell, so off-canvas artwork (e.g. a frame 4 px outside the strip) never bleeds into the neighbouring copy. The sheet outside the cells is white; each cell is filled with the canvas background colour. No separate print-sheet layer exists.
5. **Design / Print Preview** is editor state (`viewMode`), not persisted, never dirty, never in history; shown only when the project prints several copies per sheet. Preview is read-only (every project commit is refused with a message) and always starts as Design on open. Layers/Properties stay bound to the authored layers. The cut guide (dashed line, copy labels, "2-inch cut") is editor-only DOM/Konva chrome outside the printable scene.
6. **Selection geometry:** exact X/Y for a multi-selection or a group moves the topmost editable layers by translation (group boxes are derived from children, never stored); W/H scaling of a multi-selection is deferred (rotated layers, text font scaling and minimum sizes make it ambiguous). Align (6) and distribute (2) work in design coordinates on rotation-aware bounds; align targets the selection or the canvas (a single layer aligns to the canvas); distribute needs 3 layers, keeps the first item's start and the span's far edge, and equalizes gaps (negative gaps allowed). Each operation is one history step; locked layers are skipped; a group and its selected child are never both moved.
7. **Nudge:** arrow = 1 design pixel, Shift = 10, at every zoom (it was one screen pixel).
**Consequences:** canvas gradient rasterization differs by ≤1/255 between copies in a handful of pixels (translation changes gradient rounding), so "identical" means identical up to that; a project whose output cannot hold its copies shows an alert instead of a preview; no per-copy overrides exist by design. DSLR Booth export will expand the derived copies into repeated vendor Photo elements later (not implemented).

## ADR-038 — Preview photos, crop, overflow and precision canvas — Accepted (Phase 5C); items 1–2 superseded by ADR-056 (B3.1)
No schema or package change (schemaVersion stays 1).
1. **Sample photos are editor state.** A PhotoLayer is a booth capture slot; a sample is a design aid. They live in the editor store (not the project, history, dirty state or Project Assets), map by **PhotoNumber** (so repeated numbers and both two-up copies match), and are never baked into production output: only a design-preview render (`photos: 'preview'` plus a lookup) draws them; `photos: 'omit'` is the production policy (capture slots left empty). Built-in samples are generated procedurally (original code: no licensing/privacy/size concerns). User pictures come through `project:pickPreviewPhoto` (main-owned dialog, same validation as imports, bytes only, no path) and exist for the session only.
2. **Crop is editor/session state (option A).** Evidence ([../research/DSLRBOOTH_FIXTURE_ANALYSIS.md](../research/DSLRBOOTH_FIXTURE_ANALYSIS.md) §Photo): the only photo attributes are geometry and `KeepAspect` (always True; semantics Unknown/Needs Validation); no crop offset, zoom or fit attribute is Observed, so nothing shows that a booth honours a crop. A persisted crop would be a guess about vendor behaviour, so it is not stored: it survives layer/mode switches in the session, is shared by every derived copy (keyed by layer), and is dropped on project change/reopen. If a later phase proves a persisted need, a `PhotoLayer` crop field would need a schema change and migration (not proposed now).
3. **Shadow is deferred.** `PhotoLayer` has no shadow fields and the fixtures never enable `Shadow*` on photos; native shadow needs a persisted schema change (proposed fields would be `shadow: {offsetX, offsetY, blur, color, opacity} | none`). Not done; decorative treatment stays imported artwork. Frame thickness and corner radius (already in the model) are capped at half the shorter side.
4. **Artboard overflow** needs no field: geometry is never clamped (verified by tests, groups, align, duplicate, save/recovery). **Show overflow / Clipped view** is a view preference only. Output (exact render, Print Preview, per-copy cells) always clips.
5. **Shift axis lock:** 6 screen px threshold, dominant axis (ties horizontal), held until Shift is released; snapping after the lock on the free axis only; followers in a multi-drag are re-placed from the grabbed layer's final displacement (Konva's own sync ignores our constraint).
6. **Space pan** uses a capture-phase listener so the canvas never also drags; keyboard ownership rules in `canPanWithSpace`.
7. **EXIF:** Chromium's `createImageBitmap` applies the default `from-image` orientation, so common EXIF-rotated JPEGs are upright; not separately verified with real EXIF samples here (Needs Validation). **Colour management:** previews use Chromium/Konva sRGB rendering; printer ICC is future/export territory.
**Consequences:** reopening a project forgets samples and crops; Reposition is Design-mode only; no photo shadows yet.

## ADR-039 — Font discovery, requested-family preservation and fallback — Accepted (Phase 5D)
No schema or package change. `TextLayer.fontFamily` already stores a free-form family string.
1. **The requested family is the project's truth.** It is never rewritten by opening, saving, browsing the picker or rendering. Only an explicit action changes it: choosing a font in the picker, "Replace on this layer", or "Replace all uses" (one undo step; matches the primary family case-insensitively; other properties and other fonts untouched).
2. **Discovery:** the Chromium Local Font Access API (`queryLocalFonts`), which Electron 44 exposes for family/style NAMES only (no file paths; 608 faces / 206 families on the development Mac). It works on macOS and Windows with no native code, so no shell commands and no dependency. The main process now installs a permission policy: only `local-fonts`, only for the app's own pages, everything else denied (before, Electron granted all requests). There is no permission prompt to harass the user with; if the API is absent or refused the catalog status becomes `unavailable`/`denied`, nothing retries until the picker is opened again, and the UI says so.
3. **Availability** (`fontStatus`, pure, injected environment): generic families are always available; with a ready catalog the primary family decides (case-insensitive); without one a **measurement probe** (text width in the requested family vs the generic fallbacks) decides; `unknown` only while loading or if the probe cannot run. CSS fallback is never taken as evidence that a font exists.
4. **Fallback rendering:** the canvas, exact render, Print Preview and the HTML text editor all use `renderFontFamily` = requested family, then `Helvetica, Arial, sans-serif` (present on macOS and Windows; ends in a generic). One function, so a missing font falls back identically everywhere. The UI keeps showing the requested name with a "Not installed here" warning.
5. **Portability:** a `.boothproject` opened on a computer lacking a font keeps the request, shows the warning, renders the fallback and saves the request unchanged. **Distinct from export:** a future production export that rasterizes text to PNG needs the font only on the machine that exports, not on the booth PC; that is Phase 6.
6. **Embedding is deferred.** Font files carry licenses that often forbid redistribution/embedding; nothing is embedded or bundled and no font binary is in the repository. A future embed feature must check each font's embedding rights, handle file discovery (which the name-only API does not provide), package size and Windows/macOS differences, and only embed where permitted.
7. **Picker:** searchable combobox (case-insensitive substring), keyboard operable, each row drawn in its own typeface, 60 rows per page ("Show more"), installed list cached in a tiny external store (enumerated once at startup), current uninstalled font kept visible, any typed name can be requested. Weights/styles stay CSS-like (100–900, italic); per-font variant discovery is not attempted (the API lists faces but variant selection would not match every platform's resolution).
**Consequences:** the probe is heuristic (it can misjudge a font metrically identical to the fallback); an `unknown`/`unavailable` catalog limits the list to common fonts plus the project's own and says so.

## ADR-040 — Event Palette and fit-height — Accepted (Phase 5D)
No schema change: `project.palette` entries (id, role, name, hex incl. alpha) and `ColorValue` references (`literal` | `palette`) already existed on text fill, shape fill/stroke, photo frame colour and the canvas background; integrity already flags dangling references.
1. **References by id, resolved at render time.** Editing an entry's value (one history entry; picker drags coalesce; HEX commits on Enter/blur, Escape restores) recolours every linked property in Design, Print Preview and exact renders; no literal copies are made.
2. **Linking UI:** every colour field offers "Fixed color" or a palette entry; a linked field names the entry; "Use fixed color" stores the resolved literal (appearance unchanged, one undo step). Nothing converts silently.
3. **Entries:** semantic roles once each (Primary, Secondary, Accent, Background, Text), any number of custom colours; custom colours can be renamed (id and references untouched); semantic names are fixed. **Removal is refused while used** (the usage count and reason are shown); unused entries delete freely. "Add basic colors" adds the missing semantic roles with neutral values (Background copies the canvas colour). New projects are NOT pre-populated.
4. **Image palette extraction** was evaluated and deferred (feasible with canvas sampling of the existing decoded images; not needed for the manual workflow).
5. **Fit height to content** resizes only the box height to the height Konva draws the text at (shared `textLayout` config: family stack, size, width, line height, letter spacing, wrap), on explicit command, one undo step. **Persistent Auto Height is deferred** (it needs a persisted flag, i.e. a schema change).
6. **Text presets** (Title, Names/Script, Subtitle, Date, Location, Caption) are application-level, pick the first installed font from a preference list ending in a generic family, size by design height, link the colour to a palette role when the palette has it, and apply as one undo step. They are not project styles.

## ADR-041 — Production render and general export foundation — Accepted (Phase 6A)
Vendor-neutral export, built on ADR-014. No schema change, no `.boothproject` change, no new dependency. DSLR Booth XML/ZIP is NOT part of this (Phase 6B).
1. **Outputs.** *Print PNG* = the print sheet (for a 2×6 strip: the derived 4×6 with both copies); *Design PNG* = one copy of the design (offered only when the sheet holds several copies; a single-up design IS its print); *Proof PNG* = the print sheet with the current sample photos (seed, overrides, user-picked pictures and crops); *Layer package* (ZIP). Names: `<Project>-print.png`, `-design.png`, `-proof.png`, `-layers.zip` (portable stem: invalid Windows/macOS characters removed, reserved names avoided, 100 characters max).
2. **Production pixels.** Every printable layer, and each photo slot drawn as its **native frame only** (photo area empty: no placeholder tint, number, label or sample). So the print PNG is the printed result minus the booth photos. Hidden layers are not exported; artwork is clipped to the design (and to each sheet cell). Samples never appear in production output (ADR-038).
3. **Proof.** Not watermarked (owner decision). Its purpose is explicit instead: "Proof PNG", a "Not for printing" badge, a description, the `-proof` file name, unticked by default, and "NOT production artwork" in the package readme/manifest.
4. **Layer package = semantic flattening, not one PNG per layer.** The design is split by STACK POSITION relative to the photo slots (how booth templates are rebuilt) and then by type: `background.png` (opaque: canvas colour + everything behind the lowest slot), `frames.png` (native frames), `overlay.png` (non-text artwork in front of the photos), `text.png` (text in front of the photos), plus `design.png` (production reference), `proof.png` (reference, not production), `manifest.json` (format `walkone.layer-package` v1: sizes, sheet copies, stack order, files with their layer ids, photo slots in px and inches with rotation/fit/frame, fonts, notes) and `readme.txt`. Re-stacking background → photos → frames → overlay → text reproduces `design.png` exactly unless the manifest notes otherwise (artwork between slots that overlaps a later slot, text under overlapping artwork, a semi-transparent group split across files). Literal per-layer PNGs are deferred until a concrete workflow needs them. The manifest has no wall-clock time (deterministic).
5. **Preflight (vendor-neutral).** Errors block export: invalid composition, image not in the project, image that cannot be loaded, broken palette reference (would print magenta), invalid (non-positive) photo number. Warnings allow export: no visible photo slot, photo slot past the edge, layer entirely outside the design, missing font, image below 150 DPI. Notes: photo-number gaps, artwork clipped at the edge, font availability unknown, image 150–300 DPI, hidden layers. **Repeated photo numbers are valid and never reported.** DSLR Booth limits (PhotoNumber 1–12, etc.) belong to the 6B adapter.
6. **Filesystem lifecycle.** Main-owned folder picker → opaque destination id (no path ever crosses IPC; the last folder is remembered for this run). Write = verify everything first (safe single file names, PNG signature + exact size, safe flat package entries, size caps), then report conflicts (**Replace** / **Keep both** → `Name (2).png` / Cancel), then write each file atomically (temp + rename; a failure leaves the previous file intact and is reported per file). PNG density is written as a `pHYs` chunk (pixels per metre); image data is untouched. ZIP entries have fixed timestamps and order (same input → same bytes). "Show in Finder/Explorer" only for files this destination wrote.
7. **Project untouched.** Export never changes the project, its history, its Modified state or autosave.
8. **Amendment (owner decision, 2026-11-16, after manual testing): the layer package is no longer offered in the Export dialog.** The booth composites the photos into the template itself after each session, so nobody rebuilds a template by hand in Canva/Photoshop; the goal is that clients never need another editor. The dialog offers Print / Design / Proof PNGs only. The band classification, manifest and ZIP writer stay (`layerPackageOutput`, `classifyLayerPackage`, unit-tested) because the behind-/above-photo split is what the DSLR Booth adapter (6B) needs for background vs overlay artwork.
**Consequences:** export rendering runs in the renderer (Konva) and bytes cross IPC once per file (tens of MB at most for 4×6 @ 600 DPI); there is no cancel during rendering (each file takes well under a second at 300 DPI); Windows rendering parity is unverified.

## ADR-047 — DSLR Booth 7.48 export adapter — Accepted (Phase 6B)
**Context:** the owner approved Phase 6B (2026-11-16): export a Template Studio project as a dslrBooth 7.48 template ZIP, built on the 6A renderer, preflight and file lifecycle (ADR-041), with the vendor-neutral model untouched (ADR-002/003) and no schema change. Evidence: five real exports (research/DSLRBOOTH_FIXTURE_ANALYSIS.md, CONFIRMED FROM FILE) and owner-reported runtime research (research/DSLRBOOTH_748_RUNTIME_FINDINGS.md). **Decision:**
1. **Adapter location.** `src/export/dslrbooth/` (profile, `template.xml` writer/reader, container verifier, project→template plan, preflight, outputs). The domain never imports it. Main imports only the pure verifier/writer.
2. **Photo slots are native `<Photo>` elements** (PhotoNumber, integer box, whole-degree clockwise rotation about the centre; `KeepAspect="True"`, `Thickness="0"` as observed). Boxes round to the nearest pixel, or **inward** when a frame/mask image covers the edge (no photo pixel can show past the frame).
3. **Everything else is raster**, flattened in stacking order into full-canvas PNG `<Image>`s: the opaque **base** (canvas colour + everything behind the first photo) and a transparent image above each run of photos. Consecutive photos share one image above them unless their boxes overlap (stack order stays exact). **Text is always rasterized** (no text element exists in the evidence; missing fonts silently fall back on the booth PC) — the booth needs no fonts.
4. **Frames and rounded corners** are drawn into the image directly above the photo: Template Studio draws frames inside the slot, dslrBooth grows borders outward, and dslrBooth has no corner radius; a rounded slot's corners are covered with a render of what lies beneath the slot.
5. **Variants.** Main template: **native 2×6 strip** (canvas = one strip, `print_2_per_page="True"`) when the design is 2×6 on a two-up 4×6; otherwise the design (single-up) or the full sheet. A strip also offers the **4×6 sheet** (both copies pre-placed, `print_2_per_page="False"`, photos repeated with " Copy" names) — the structure of the owner's hand-built templates, kept as a fallback until 6C validates the native strip.
6. **Package format** copied from the fixtures: `template.xml` UTF-8 with BOM, CRLF, observed declaration/attribute order/defaults, elements in descending ZIndex (0..N-1, unique), `<X ... />`, no trailing newline; flat ZIP, all entries deflated, case-insensitive alphabetical order, fixed timestamps; `preview.png` (placeholders with numbers) at canvas size. ZIP name = template `Name` (`<Project>.zip`, `<Project> 4x6.zip`). Root: `Dimensions="0"`, `IsLegacy="True"`, `PrintToSecondaryPrinter="False"`, `LastSavedDate` local US format, `Id` 25 alphanumeric characters derived from project id + variant (stable across re-exports), `OriginalDevice="WalkOneTemplateStudio"` (no machine name), `IsLocked="False"`.
7. **Preflight (dslrBooth only, when selected):** errors — no photo slots (ADR-045), PhotoNumber > 12; warnings — slot fit not Cover (dslrBooth always fills), photo opacity (not exported), resolution other than 300/600; notes — rotation, flattening, the native strip's two-up.
8. **Verification before writing:** the main process re-reads `template.xml` (structure, BOM, every image present and referenced, unique ZIndex, PhotoNumber 1–12, ≥1 photo) and verifies every PNG's pixel size like any export.
**Needs Validation (Phase 6C, real Windows install):** that dslrBooth imports the ZIP; the native strip with `print_2_per_page="True"` and `Dimensions="0"` (only 4×6 canvases were seen); rotation pivot; behaviour of a re-imported template with the same `Id`; preview requirements; printing/cut on the DNP printer. **Consequences:** templates are not editable as separate artwork layers in dslrBooth's editor (by design: edit in Template Studio, export again). Native text, native images with KeepAspect, and native borders remain possible later if 6C or new fixtures confirm their attributes.

## ADR-048 — DSLR Booth template importer — Accepted (Phase 6D, 2026-11-17)
**Context:** the owner approved the importer (ADR-046: "NEEDED"; dslrBooth users start from existing templates). Evidence: the five real exports (research/DSLRBOOTH_FIXTURE_ANALYSIS.md) and the 7.48 runtime findings. No schema change: ADR-017 `sourceCompatibility` is populated for the first time. **Decision:**
1. **Pipeline.** Main picks the ZIP (no path crosses IPC; the renderer gets an opaque token), reads it in memory (`src/projects/dslrImport.ts`: ≤ 500 entries, ≤ 4 MB XML, ≤ 256 MB per picture, ≤ 1 GB total; unsafe paths, links, encryption refused; `template.xml` at the top or inside ONE folder, `__MACOSX`/`.DS_Store` ignored), checks every referenced picture like any image import, and hands bytes + facts to the pure mapper (`src/import/dslrbooth/`: strict-but-tolerant XML reader that rejects DTDs; template reader; two-strip detection; mapper). Step 2 (commit with the chosen layout) creates a new, never-saved project through `ProjectService.createNew`.
2. **Mapping.** Canvas = Width/Height at Resolution (inches derived); `BackgroundColor` ARGB → hex; `<Photo>` → photo slot (PhotoNumber, box, rotation, opacity, visibility, lock; Cover; a non-zero border becomes an inside frame with the slot grown by the border, never seen in a real file); `<Image>` → image layer with a project asset (one per distinct content, SHA-256), `KeepAspect` True → Fit / False → Stretch, role by heuristic (large and behind the first photo → background, large and in front → overlay, else graphic); stacking by ZIndex (ties/missing → file order); `print_2_per_page="True"` on a portrait design → two-up output.
3. **Two strips side by side** (the owner's hand-built 4×6 sheets): detected when every right-half element repeats a left-half one (same photo number/picture, within 2% of the strip width). Default: **one 2×6 strip printed two-up** (the left strip is kept; the right copies are kept verbatim in the import notes) when the copies match; **the sheet as is** when they differ (rotation, opacity, visibility, stacking), with the differences listed. The user can choose either. Hand-placement offsets of the copy are reported, not silently evened out.
4. **Never silently discarded:** unknown elements/attributes, enabled shadows, photo KeepAspect False, unreadable/missing pictures, invalid elements and dropped copies go to `sourceCompatibility.dslrbooth` (`project.rootAttributes` without `OriginalDevice`, `layers[id].attributes`, `unmapped`) and the import report. `OriginalDevice` (a machine name) is dropped and the report says so. Edits prune per-layer entries whose layer was deleted (`editor/compatibility.ts`), so imported projects stay valid.
5. **Not used by the exporter yet:** re-export generates its own `Id` (ADR-047) and flattens as usual; whether to reuse the original `Id` is a 6C question.
**Consequences:** imported text/artwork stays raster (dslrBooth stored it flattened). Matching is measured against each template's own preview (validate-import.js).

## ADR-049 — Template Studio remains standalone and becomes a shared full-spec module of WalkOne Booth — Accepted (owner, 2026-11-17)
**Context:** the owner wants to replace their dependency on dslrBooth with **WalkOne Booth**, a complete local, Windows-first photo booth platform (events, capture, camera, printing, sharing incl. SMS, media, operator dashboard, event readiness, booth health). Template Studio already exists as a standalone desktop editor, and it is still valuable on its own: designing away from the booth PC, on macOS or Windows, client proofs, revisions, dslrBooth export during the migration, and staff who only design. ADR-042 left the long-term shape open. Full direction: [PRODUCT_ECOSYSTEM.md](PRODUCT_ECOSYSTEM.md).

**Alternatives considered:**
1. *Template Studio only as a module of WalkOne Booth* (retire the standalone app). Rejected: designing away from the booth PC and on macOS would need the whole booth runtime; staff who only design would carry camera/printer/sharing machinery; dslrBooth users during the migration lose their editor.
2. *Two editors*: keep standalone Template Studio and write a separate editor inside WalkOne Booth. Rejected: two implementations of the domain, rendering, typography, safe-area and export logic would drift; templates would need conversion; every fix would be made twice; output could differ between the app that designed a template and the app that prints it.
3. *Standalone only, with WalkOne Booth importing exported packages.* Rejected: operators would bounce between apps and re-enter event data; editing an event's template from the booth would not be possible.
4. **Hybrid (chosen):** one shared Template Studio core, shipped both as the standalone app and as a full-capability module inside WalkOne Booth.

**Decision:**
1. **Template Studio stays a first-class standalone product.** It is never reduced to a thin screen that needs the booth runtime installed.
2. **WalkOne Booth embeds the same Template Studio at full capability.** Functional parity wherever practical: a standalone template opens in WalkOne Booth without conversion, and a template edited in WalkOne Booth stays a normal Template Studio project.
3. **One editor, never two.** A single shared core owns the `TemplateProject` model, rendering (canvas, proof, production), editor behaviour, typography, palettes, assets, photo slots, composition, preflight, safe-area logic, the native WalkOne template format and the dslrBooth adapter. A second template editor is prohibited, because it would drift (alternative 2).
4. **Integration behaviour (future):** opened from an event, Template Studio receives the event context (name, date, client, venue, format, output profile, company profile, branding, palette, approved version) and returns the saved native template to Event Setup, where Event Readiness validates it.
5. **Separation of concerns:** company profile, output/printer profiles, sharing credentials and event data are **not** part of `TemplateProject`; templates may reference them. `TemplateProject` stays vendor-neutral and is never restructured around dslrBooth (ADR-002).
6. **WalkOne Booth architecture style:** a modular monolith with explicit internal module boundaries, Windows-first; SMS/email/QR sharing lives in its Sharing Service (never in Template Studio), with OS-backed credential storage and offline queues.
7. **Package boundary:** a likely future split into `apps/template-studio`, `apps/walkone-booth` and `packages/{template-domain, template-editor, template-renderer, template-export, output-profiles, shared-ui, shared-contracts}` is **conceptual only**; the repository is not reorganised now.

**Consequences:** new Template Studio work must keep today's seams intact (pure domain with no Electron/React; editor state behind injected ports; typed IPC contracts; adapters outside the domain), so that a later extraction is a move rather than a rewrite. Features that both surfaces need (output profiles, company profile, safe-area check, proof/approval) are designed once for both. The product spec's "not a photo booth runtime / not a replacement for DSLR Booth" non-goals continue to apply to **Template Studio**; the runtime belongs to WalkOne Booth.

**Migration implications:** today Template Studio ↔ dslrBooth 7.48 (export 6B, import 6D); later Template Studio → native WalkOne Booth template/runtime package (format not designed; the runtime representation may differ from `.boothproject`); once WalkOne Booth is primary, dslrBooth support remains a legacy interoperability adapter.

**Not approved by this ADR:** starting WalkOne Booth development, extracting packages, creating a monorepo or a new repository, the native runtime format, any sharing/SMS code, any change to `TemplateProject`, `.boothproject` or export behaviour. Phase 6C (Windows + DNP validation) remains the immediate work.

## ADR-050 — Phase 6C results: observed-only recording, live-text import plan, Windows fixes — Accepted (owner, 2026-11-17)

**Status:** implemented and verified on macOS. **Stabilization (2026-11-18, owner brief):**

## ADR-052 — Text overflow mode (no-wrap / clip to box) — OPEN (proposed 2026-11-18, needs owner approval)
**Context:** dslrBooth cuts a line wider than its text box off at the box edge (observed, synthetic fixture T13). Template Studio text always wraps by word (`textLayout`, `wrap: 'word'`), so such an imported line spills below its box, over or under other layers (Windows re-test: about 8 lines, partly under a photo slot). Konva can draw a single unwrapped line clipped to the box (`wrap: 'none'` plus a clip region), and the production render and export use the same drawing code, so the renderer is capable. What is missing is a **persisted, vendor-neutral setting on the text layer** saying "this text does not wrap and is clipped to its box". Reading the dslrBooth import notes (`sourceCompatibility`) in the renderer would make the vendor format drive rendering, which the architecture rules forbid.
**Proposal:** add `overflow: 'wrap' | 'clip'` to `TextLayer` (default `'wrap'`, so every existing project draws exactly as today), a `schemaVersion` bump with a migration that adds the default, an inspector control ("Wrap text" / "Cut off at box edge"), and the importer setting `'clip'` for dslrBooth live text (which never wraps in dslrBooth). Edit-in-place, Fit height to content and the transformer would treat a clipped text as one line. Export stays rasterized.
**UX input (Phase 7A, 2026-11-19):** one "When text is longer than its box" control with Wrap / Grow box to fit / Shrink text to fit / Keep on one line, cut at box edge; Clip (dslrBooth parity) and Shrink to fit (Design Guide names) recommended first; each persisted mode needs schema approval ([PHASE_7A_UX_ARCHITECTURE.md](PHASE_7A_UX_ARCHITECTURE.md) §20). Still OPEN.
**Until decided:** imported over-long text wraps, nothing is removed, and the import note explains the difference and the fix. **No schema change is made without approval.**

## ADR-053 — Output Profiles remain separate from TemplateProject and drive physical-output preflight — Accepted (owner brief, 2026-11-18)
**Context:** the owner requires an automatic safe-area / 2-inch-cut check (ADR-044 direction, PRODUCT_SPEC). Phase 6C Stage 1 observed the first printer facts on the Windows research laptop (DNP DS-RX1, driver 1.1.1.0, `CUT_2INCH`, print margin off, one borderless 156.1 × 105.0 mm page for the `_2x` sheet) and inferred, but did not measure, about 1.6–1.8 mm of trim; the interim guidance is 3 mm from strip edges and the cut. The measurement-print readout is still pending. ADR-049 requires printer/output configuration to stay outside `TemplateProject` and be shareable with the future WalkOne Booth.
**Decisions:**
1. **Separate model:** an **Output Profile** (`walkone.output-profile` v1) describes the sheet (in Template Studio's orientation), what it holds (one design or copies in a grid), cut positions, the expected loss at each sheet edge and at a cut (trim), keep-safe margins for the edges and the cut, finishing results (auto-cut, cut on seam, gutter), device/driver/media facts, setup guidance, observed and verified environment/date, and notes. It lives in the pure module `src/output/` (alias `@output`; depends on `@domain` only, no Electron/React/DOM), never inside `TemplateProject`, and contains no PrintTicket or driver data blobs.
2. **Evidence on every physical value:** `unknown` · `nominal` · `inferred` · `provisional` · `observed-test-laptop` · `owner-measured` · `verified-production`. A value is `null` exactly when it is `unknown`. Only owner-measured and production-verified count as verified; anything else shows a "provisional"/"not measured" note in the checks.
3. **First profile, bundled as data:** `src/output/profiles/dnp-ds-rx1-6x4-2inch-cut.json` ("DNP DS-RX1 · 6×4 PC · 2-inch cut · borderless"), validated by the schema at load. Device, driver, driver page, borderless and the 2-inch cut setting: *observed on test laptop*; trim 1.8 mm top/bottom and 1.6 mm at the outer edges: *inferred*; trim at the cut and all finishing results: *unknown*; keep-safe 3 mm (edges and cut): *provisional*; overall *provisional*; not verified on the production booth. The owner's readout is entered by editing this file (values, evidence, confidence); no code change.
4. **Selection is an app preference, not project data:** editor state (`outputProfileId`, `showSafeAreas`), kept when another project opens, remembered per computer in the renderer's storage (`walkone.outputProfile.v1`; works without it). Choosing a profile never changes the project, its history or Modified state. **No schema or `.boothproject` change.** A per-project profile reference would need a schema change and separate approval.
5. **Geometry in physical units first:** millimetres → pixels at the project's own DPI (3 mm = 35.43 px at 300 DPI, 70.87 px at 600 DPI), no rounding. The sheet's boundaries (edges, cuts) are mapped into each copy of the authored design and merged, so the ONE logical 2×6 strip carries the stricter of "outer edge" (one copy) and "centre cut" (the other) on both sides; Print Preview shows the sheet with each copy's zones.
6. **Checks:** critical content = text (its drawn lines, measured with the canvas text layout), images with role logo or badge, and photo slots. Backgrounds, overlays, frames, graphics and shapes are never reported. **Warning** when critical content crosses a cut, enters the expected trim or the keep-safe margin (distance in mm, the edge named); **info** for no profile, a provisional/unverified profile, and "all critical content inside"; a profile for a different sheet is a warning and disables the overlay; a cut running through the design is a warning. No safe-area finding is an error or blocks export.
7. **Never exported:** exported templates and PNGs stay printer-neutral; the overlay is editor-only.
**Not decided here:** custom/duplicated profiles and a profile editor, printer discovery, driver-ticket capture, certification history, a per-project profile reference (schema), output-profile storage shared with WalkOne Booth (ADR-012 / PRODUCT_ECOSYSTEM §12 open question), and fixes offered from the warnings ("move inside the safe area").

**Update (2026-11-19, owner, B1 V8):** the owner's test print on the research printer looked right (both strips matched, clean automatic cut, no white gutter). Recorded in the DS-RX1 profile as *observed* evidence; the profile's status is now "Observed on test laptop" and the owner rules it ready for production use. Trim values stay *inferred*, keep-safe 3 mm stays *provisional*, nothing is marked measured or production-verified. A full printer-profile scope (a list of booth printers, or detecting the printer) is future work.

## ADR-055 — UI themes and density use semantic design tokens and application-level preferences — Accepted (owner brief, Phase 7B B2, 2026-11-19)
**Context:** the owner approved the B1 round 2 mockups (Light default, Dark available, Match system, Comfortable default with Compact available, bundled Inter, restrained kind colours, theme-independent canvas overlays). Before B2 the app had one dark token set (`tokens.css`) used by ~560 component declarations.
**Decision:**
1. **Three token layers** in `src/renderer/src/styles/tokens.css`: primitives (`--p-*`, never used by components except pure white for the switch thumb), semantic tokens (`--c-surface-*`, `--c-text-*`, `--c-border-*`, interaction, accent, status error/attention/info/ready fg+bg+border, `--c-kind-*`, `--shadow-1..3`, `--shadow-artboard`, `--c-scrim`) redefined per theme, and components that consume semantic tokens only. Pre-7B names (`--c-app`, `--c-text-2`, …) are aliases of the semantic names, so existing CSS migrated without a rewrite.
2. **Themes:** Light is the bare `:root` default; `data-theme="dark"` on `<html>` switches. **Match system** is resolved in JS (`prefers-color-scheme`, live) so CSS only sees `light` or `dark`; Electron's `nativeTheme.themeSource` follows the choice (IPC `app:setNativeTheme`) so the native title bar/menus match. Switching is live; no restart.
3. **Density:** `data-density="comfortable"` (default: 34 px controls, 38 px large buttons, 36 px rows, 80 px rail, 52 px top bar, 48 px view bar, 40 px section headers, 30 px status bar, 14 px text — the approved round 2 values) or `"compact"` (the pre-7B sizes). Both define exactly the same `--d-*` tokens; the structure never changes.
4. **Interface scale** (90/100/110/125 %) is a preference and a token multiplier (`--ui-scale`) on token-driven sizes. It is distinct from OS display scaling and canvas zoom and never uses page zoom (which would distort canvas maths). B2 ships the preference, validation and token plumbing only; sizes still hard-coded in component CSS follow in B3+, and no UI exposes the scale yet.
5. **Preferences** (`theme`, `density`, `uiScale`, `showGettingStartedTips`) are **settings of this computer**, kept in the renderer's browser storage under `walkone.appearance.v1` next to the Output Profile choice (ADR-053). They are never in `TemplateProject`, `.boothproject`, exports, undo history or the Modified state. Damaged values fall back field by field.
6. **Canvas overlays** (selection, snap guides, safe line, trim, flags, cut, halo) use the same hues in every theme (`--p-ov-*`, mirrored by `canvasTheme.ts`); trim is the muted amber approved in B1 (V6). Artwork is never themed. The editor-only veil outside the artboard fades toward the theme's canvas surround.
7. **Inter** is bundled (`@fontsource-variable/inter`, SIL OFL 1.1) as `'Inter Variable'` for interface chrome only, emitted next to the renderer bundle; no web font service. Project text keeps its own fonts; the UI family name cannot collide with a project font named "Inter".
8. **Evidence and severity language:** evidence tiers (Verified / Observed / Estimated / Reference / Unknown) drive icon and tone while badges keep the precise level word; the friendly meter (Estimated → Tested on a print → Measured) and "Ready to use" summarise but never replace the evidence model ("Measured" is not "Verified on production booth"). Severity reads Error / Needs attention / Good to know / Ready; notes alone read "Ready · N notes".
**Consequences:** later 7B work (B3+) builds screens from the shared primitives and tokens; a third theme or high-contrast mode is a token block, not a component rewrite. Settings › Appearance (B5) replaces the interim View-menu items. Not decided here: high-contrast mode, user-chosen accent colours, per-project UI preferences (none planned).

## ADR-057 — New text defaults to Arial; the bundled interface font is not a design font — Accepted (owner brief, Phase 7B B5, 2026-11-21)
**Context:** new text layers asked for **Helvetica**. Helvetica is not installed on Windows, so on the Windows test laptop every new text immediately raised a missing-font note (B4.1 observation). The owner asked B5 to choose a cross-platform default that needs no network, does not trigger the check on Mac or Windows, and never rewrites existing or imported fonts. The bundled interface font (Inter, `@fontsource-variable/inter`, ADR-055) was the preferred candidate if it could safely carry design content.
**Findings (code, 2026-11-21):**
- The font check reads the computer's INSTALLED families (`queryLocalFonts`). Inter is bundled as a web font for the interface only, so it is not installed: a design asking for "Inter" would be reported missing on every machine.
- The canvas, Print Preview and every export render with the requested family through the renderer's font stack. The exact render does not wait for web fonts to load, and the bundled face is named "Inter Variable", not "Inter". Using it for designs would need a font-loading guarantee, a name mapping and the font library (ADR-044), which are not B5 work.
- dslrBooth exports always draw text as pictures (`export/dslrbooth/plan.ts`), so the booth PC needs no fonts. Portability depends only on the font being present where the design is edited and exported.
- Arial ships with macOS and Windows, is already the second entry of the render fallback stack (`Helvetica, Arial, sans-serif`), and the font picker lists it on both.
**Decision:**
1. New text layers ask for **Arial** (`DEFAULT_TEXT_FONT`, `editor/newLayers.ts`).
2. Only NEW layers use it. Existing text, saved projects and imported dslrBooth text keep the family they store (ADR-039): nothing is rewritten on open, import, save or export. Text style presets keep their own font lists (first installed wins).
3. Inter stays the interface font only. Making a bundled font available to designs is part of the font library (ADR-044), with load-before-render and portability rules.
**Consequences:** a new text no longer shows a missing-font note on Windows or macOS. A project created before B5 still asks for Helvetica and shows the note on Windows until the operator picks another font (unchanged, honest behaviour). No schema change. Mac verification: the B5 suite (checks 21–24); Windows confirmation: the B5 Craft Anything run.

## ADR-059 — Custom formats: one format model, optional composition fields (schema version 2, ADR-060), generic design safe margin, app-local My formats — Accepted (owner B5.5 visual checkpoint, 2026-11-22, with the schema-version amendment)
**Context:** B5.5 adds a Custom Size wizard (magnets, keychains, wallet prints, squares, custom sheets). Before B5.5 the domain could express exact size (`single`) and a centred `grid` with ONE gap, but not sheet margins, separate row/column gaps or a top-left placement. The brief asks for the smallest coherent extension, three separate concepts (Format · Output Composition · Output Profile), no schemaVersion bump unless unavoidable, and no TemplateProject change for what can live elsewhere.
**Decision:**
1. **Format model.** `FormatDefinition` (`src/domain/print/format.ts`): design width/height in INCHES (canonical, unrounded) + integer DPI + the unit it was entered in (display only) + arrangement (`exact` | `repeat` | `custom` sheet: sheet size, columns, rows, column gap, row gap, four margins, centred/top-left) + generic safe margin (mm or none) + cut-guide preference. Built-in formats (2×6 strip, 4×6, 6×4 at 300/600) are immutable definitions over the existing presets. **One creation path:** `createProjectFromFormat` → `createProject`; a built-in format creates exactly the project its preset always created (unit-tested byte for byte).
2. **Output composition (TemplateProject, optional fields).** The `grid` layout gains optional `rowGap`, `margins {top,right,bottom,left}` (inches) and `align: 'center'|'start'`. Absent = pre-B5.5 behaviour (row gap = gap, no margins, centred); writers omit default values (`normalizeGridLayout`), so standard projects serialize exactly as before. Composition is what must persist to reproduce the print, so it stays in the project where it already lived.
3. **Generic design safe margin (TemplateProject, optional).** `canvas.safeMarginMm` (0–50 mm): a FORMAT's own "keep critical content this far from every design edge" guidance (wizard default 3 mm for physical formats, none for pixel formats). It carries no printer evidence and is labelled "generic … not a measurement of any printer" everywhere. It is deliberately **not** the Output Profile safe margin of §11 of DATA_MODEL: printer-specific trim, cuts and keep-safe distances stay in Output Profiles (ADR-053) and, when a fitting profile is selected, **supersede** the generic margin (the generic check and overlay are used only without a fitting profile). Stored in the project because it belongs to the format the project was made with and must survive save/reopen and moving the file to another computer; an app-local store keyed by project would be lost or mismatched.
4. **Schema version 2 for files that use the new fields (amended at the owner review; policy in ADR-060).** Every new field is optional with a defined default; no field became required; unknown keys are still rejected. Because older builds reject unknown keys, a file that USES a new field cannot be parsed by a pre-B5.5 build, so it is written as `schemaVersion: 2` and an older build refuses it with "this app supports up to 1. Update the app". A file that uses none of them is still written as `schemaVersion: 1`, byte-identical to before (tests), so standard 2×6 / 4×6 / 6×4 projects stay readable by older builds. Migration 1 → 2 only re-labels (a v1 document is a valid v2 document). *(The first draft kept every file at v1; the owner rejected that because two incompatible shapes would share one version number.)*
5. **Cut guides are editor guidance, not project data.** "Show cut guides in Print Preview" is an app view preference (View › Cut guides; on by default, as Print Preview always showed the strip's centre cut). Never rendered into any PNG or dslrBooth output.
6. **My formats are app-local.** Saved custom formats live in the app-data `formats.json` (`FormatPresetStore`), holding only the format definition (no artwork, layers, palette, photos or client data; the schema is strict). Rename/delete with confirmation; built-ins are not stored and cannot be deleted. Future Company Formats would be another source of `FormatDefinition`s merged into the same picker (extension point); no sync, no Company Profile.
7. **dslrBooth only for proven sizes.** The exporter can write any pixel size, but dslrBooth 7.48 has only been shown 2×6 strips and 4×6/6×4 prints/sheets (and templates imported from dslrBooth). Other custom sizes get no dslrBooth output, with a plain "Good to know" reason; PNG export stays available for every format. No dslrBooth paper definitions are invented.
**Alternatives rejected:** keeping every file at schemaVersion 1 (two shapes under one number; an old build would answer with a schema error instead of "Update the app"); a separate custom-project type or editor mode (ADR-049: one editor); storing the safe margin or cut guides in an Output Profile (a format is not a printer; a PNG-only workflow has no printer); app-local per-project storage of composition (not portable).
**Consequences:** unit tests for conversion, validation, composition, creation, persistence and backward compatibility; the built-app suite `validate-7b-b55.js`; DATA_MODEL §3/§11 updated. **Owner decision (2026-11-22):** the visual/product checkpoint is approved as implemented, including item 3 (the generic safe margin is design guidance, not printer evidence, and may be persisted in the project; a matching Output Profile takes precedence) and item 7 (dslrBooth only for proven sizes); item 4 amended to schema version 2 under ADR-060.

## ADR-060 — Schema-version policy: a file carries the oldest version that can read it — Accepted (owner B5.5 architectural review, 2026-11-22)
**Context:** ADR-005 introduced `schemaVersion` with forward migrations; `project.ts` said "bumped on any breaking change"; the loader rejects newer versions with "Update the app", and rejects (never drops) unknown fields (DATA_MODEL §8). The project had no explicit rule for OPTIONAL additions. B5.5 first kept such additions at v1, which meant a B5.1 build and a B5.5 build both called their files v1 although B5.1 could not parse every B5.5 file. The owner asked for the rule to be settled before B5.5 was committed.
**Findings:** (1) the version was meant to identify file shapes a reader can safely parse: the loader's only forward-compatibility mechanism is the version check, and it exists to give "Update the app" instead of a schema error; (2) "breaking" was never limited to required fields; (3) no optional-field policy existed (DATA_MODEL §12 only said additive changes "will bump schemaVersion when they change existing shapes"); (4) older builds are expected to reject newer projects, cleanly; (5) with strict unknown-field rejection, ANY persisted field an older reader does not know is a breaking change for that reader, optional or not.
**Decision:**
1. **Meaning.** `schemaVersion` in a file is the oldest file-format version whose readers can parse that file. A reader supporting version N opens every file marked ≤ N and refuses every file marked > N with "Update the app".
2. **When to bump.** Increment `CURRENT_SCHEMA_VERSION` whenever an older reader would reject or misread a file the new writer can produce: a new field (optional or required), a new enum value or layer type, a changed meaning, a removed or renamed field. Optional additions are NOT exempt while unknown fields are rejected. Changes that never reach the file (app preferences, app-local stores such as My formats, Output Profiles) do not bump it.
3. **Writers stamp the lowest version that represents the content** (`fileSchemaVersion` in `src/domain/project/serialization.ts`, the one place that knows which fields need which version). A project that uses no newer feature stays at the older version, byte-identical, so it remains openable by older builds. A future change that every file must carry (e.g. a new required field) simply makes that version the minimum for all files.
4. **In memory a project is always at `CURRENT_SCHEMA_VERSION`.** Loading runs the migrations N → N+1 in order; each migration is pure and adds only what the newer shape needs (defaults where the meaning would otherwise change). Opening never rewrites the file; only an explicit save writes, with the stamped version.
5. **Mislabelled files fail.** A file whose content needs a newer version than it declares is refused (`schema-version-mismatch`, shown as invalid or damaged) instead of being accepted silently.
6. **Each bump ships** a migration entry, a stored sample at the previous version under `tests/fixtures/projects/schema-vN/` (written by the last build of that version) and tests (open → same geometry → save back byte-identically; newer version refused), in the same change, plus a line in the version history below.
**Version history:** **1** — original format (Phases 1–7B B5.1). **2** — Phase 7B B5.5 (ADR-059): optional `output.layout` grid `rowGap`, `margins`, `align` and optional `canvas.safeMarginMm`; migration 1 → 2 only re-labels.
**Consequences:** support can tell from the number alone which build is needed to open a file; standard projects made or saved by B5.5 remain readable by B5.1 builds; only files using custom-layout or safe-margin features need B5.5 or later.
